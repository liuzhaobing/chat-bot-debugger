## 2. 技术难点分析

### 2.1 Agent Planning 能力（P0难度）

这是整个方案的核心难点，涉及：

```
宏观任务 → 意图理解 → 设备定位 → 协议加载 → 场景生成 → 执行 → 报告
```

**具体难点**：

- **意图理解**：用户说"测试 CQ928 的语音控制能力"，Agent 需要理解：
  - CQ928 是什么设备类型？
  - "语音控制能力"包含哪些测试维度？

- **设备定位**：需要从 IOT 平台设备列表中匹配设备，但设备名称可能不唯一

- **场景生成**：LLM 需要根据协议的 `properties` 和 `functions` 自动生成有意义的测试场景

**建议方案**：

```python
# 采用结构化 prompt + 少样本学习
SCENARIO_GENERATION_PROMPT = """
设备协议：{protocol}
测试重点：{focus}

请生成测试场景，格式如下：
[
  {
    "scenario_name": "开关机测试",
    "query": "打开油烟机",
    "expected_state_changes": {"workStatus": {"from": "0", "to": "1"}},
    "expected_keywords": ["已打开", "好的"]
  }
]
"""
```

### 2.2 场景生成的覆盖度和有效性（P1难度）

**难点**：
- 如何保证生成的测试场景覆盖所有设备功能？
- 如何避免生成无效场景（如设备不支持的功能）？
- 如何对场景进行优先级排序？

**建议**：
- 采用协议约束 + LLM 生成混合模式
- 协议中的 `functions` 字段直接映射为测试场景基础
- LLM 负责生成自然语言查询和预期结果

```python
class ScenarioGenerator:
    def generate_scenarios(self, protocol, focus):
        # 1. 从 functions 提取基础场景
        base_scenarios = self._extract_from_functions(protocol)
        # 2. LLM 丰富查询语句和预期
        enriched = self._llm_enrich(base_scenarios, focus)
        return enriched
```

### 2.3 验证判定的可靠性（P1难度）

当前设计：

```python
# 权重分配
IOT状态验证：70%
语音响应验证：30%
```

**难点**：
- IOT 状态查询有延迟，可能需要多次重试
- 语音响应（ASR）可能有识别错误
- 音响可能返回非预期但实际正确的响应（如同义词）

**建议**：
- 增加 LLM 语义相似度判断（替代简单关键词匹配）
- 引入验证重试和超时机制
- 支持人工介入判定

### 2.4 测试报告生成（P2难度）

**难点**：
- 如何量化测试结果（通过率、覆盖率）？
- 如何记录失败案例的上下文（音频、ASR结果、IOT状态）？
- 如何生成可读性强的报告？

## 3. 架构风险评估

### 3.1 高风险项

#### 3.1.1 过度依赖 LLM 的理解能力

- 场景生成完全依赖 LLM 理解协议
- 如果 LLM 理解错误，可能导致无效测试场景

**缓解措施**：协议文件增加 `test_templates` 字段，提供测试模板

#### 3.1.2 语音交互的不确定性

- 音响响应时间不可控
- 环境噪音影响 ASR 准确率

**缓解措施**：增加 VAD 灵敏度调节，支持重试

### 3.2 中风险项

#### 3.2.1 IOT 平台集成

- 依赖第三方 IOT 平台 API 稳定性
- 设备状态更新可能有延迟

**缓解措施**：已有重试机制，可考虑增加缓存

### 3.3 低风险项

#### 3.3.1 协议管理

- 静态 JSON 文件，Git 版本控制
- 已实现的加载器/解析器稳定
