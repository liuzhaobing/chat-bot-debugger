## 测试用例编写规范

本规范定义了测试用例各字段的编写标准，确保测试用例的一致性、可读性和可执行性。


### 1. 用例编号 id

#### 1.1 格式规范

- **标准格式**：`模块缩写 - 类型 - 序号` 或 `项目 - 模块 - 序号`
- **示例**：
  - `USR-LOGIN-001`
  - `ORDER-PAY-015`
  - `API-USER-003`

#### 1.2 编写规则

1. **全局唯一**：编号不可重复
2. **保持连续性**：删除用例后编号不重复使用
3. **预留扩展**：建议使用 3-4 位序号，预留扩展空间

#### 1.3 常见错误

避免以下编号方式：

- `001` — 缺少模块信息
- `test1` — 命名不专业
- `登录 -1` — 含中文，不利于系统管理


### 2. 测试模块 module

#### 2.1 格式规范

- **标准格式**：一级模块 - 二级模块（最多三级）
- **示例**：
  - `用户中心 - 登录注册`
  - `订单管理 - 支付流程 - 优惠券`

#### 2.2 编写规则

1. **保持一致性**：与产品功能模块结构保持一致
2. **粒度适中**：一个模块下的用例数建议 10-50 条
3. **标准命名**：使用标准命名，禁止随意简写

#### 2.3 注意事项

- 需提前与团队统一模块划分，形成模块清单


### 3. 用例标题 title

#### 3.1 格式规范

- **标准格式**：【动作】+【对象】+【场景/条件】（结果可省略）
- **示例**：
  - `输入正确手机号和验证码完成登录`
  - `库存不足时提交订单提示缺货`

#### 3.2 编写规则

1. **简洁概括**：一句话概括，不超过 30 字
2. **独立可读**：标题本身可判断测试目的，不依赖步骤
3. **具体明确**：避免模糊词汇，"正常"、"正确"、"异常"需具体化

#### 3.3 常见错误

避免以下标题方式：

- `测试登录功能` — 太泛，无法判断具体测试内容
- `登录 - 正常场景` — 不具体，缺乏可操作信息
- `验证系统是否能正确处理各种情况` — 空话，无实际意义


### 4. 前置条件 preconditions

#### 4.1 内容定义

执行本用例前必须满足的环境、数据、状态要求。

#### 4.2 示例

```
1. 已注册账号：test@example.com / 123456
2. 账号未登录状态
3. 网络连接正常
4. 后台已配置商品 A，库存≥1
```

#### 4.3 编写规则

1. **逐条列出**：编号清晰，每条独立
2. **数据具体**：涉及测试数据需具体（账号、ID、金额等）
3. **区分步骤**：前置条件是"准备"，步骤是"操作"，两者需区分开

#### 4.4 注意事项

- 若无需特殊准备，填写"无"或"-"，勿留空


### 5. 步骤描述 steps

#### 5.1 格式规范

- **标准格式**：1, 2, 3... 编号步骤，一步一操作
- **示例**：
  ```
  1. 打开登录页面
  2. 输入手机号：13800138000
  3. 点击【获取验证码】按钮
  4. 输入收到的验证码：123456
  5. 点击【登录】按钮
  ```

#### 5.2 编写规则

1. **原子化操作**：一个步骤只做一个操作
2. **包含数据**：包含具体数据：输入值、点击对象、选择项
3. **可执行性**：新人按步骤能独立完成
4. **长度适中**：一般 3-8 步为宜，过长需拆分用例

#### 5.3 编写技巧

使用明确动词描述操作：

- 点击
- 输入
- 选择
- 查看
- 验证
- 提交


### 6. 预期结果 expect_results

#### 6.1 格式规范

- **标准格式**：与步骤对应，或整体描述验证点
- **示例**：
  ```
  1. 页面跳转至首页
  2. 右上角显示用户昵称"测试员"
  3. 本地存储生成 token 字段
  4. 数据库 login_log 表新增一条记录
  ```

#### 6.2 编写规则

1. **可验证**：结果需客观可判断，避免"显示正常"、"响应快速"等主观描述
2. **完整性**：覆盖 UI、数据、接口、日志等多维度
3. **精确性**：包含具体文字、数值、状态码

#### 6.3 常见错误

避免以下预期结果：

- `登录成功` — 不具体，无法判断成功标准
- `页面显示正确` — 无法验证，缺乏具体标准
- `系统处理数据` — 无标准，无法判断是否完成


### 7. 实际结果 actual_results

#### 7.1 填写时机

用例执行时填写。

#### 7.2 内容定义

客观记录实际发生的现象。

#### 7.3 示例

- `页面跳转至首页，但昵称显示为"null"`
- `接口返回 500 错误，Error: DB connection timeout`

#### 7.4 编写规则

1. **如实记录**：不加工、不推测原因
2. **详细记录**：与预期不符时，详细记录现象、错误信息、截图/日志编号
3. **通过标记**：通过时填写"与预期一致"或"Pass"

#### 7.5 注意事项

- 这是执行证据，需保证可追溯


### 8. 测试结论 test_result

#### 8.1 可选值

- **Pass**：通过
- **Fail**：失败
- **Block**：阻塞
- **N/A**：不适用

#### 8.2 定义说明

- **Pass**：实际结果完全符合预期
- **Fail**：实际结果与预期不符（需关联缺陷）
- **Block**：因阻塞问题（如 Bug、环境）无法执行
- **N/A**：用例不适用当前版本/场景

#### 8.3 填写规则

1. **单选原则**：只能单选，禁止"Pass/Fail"模糊状态
2. **关联缺陷**：Fail 时必须关联缺陷 ID
3. **阻塞说明**：Block 时需注明阻塞原因和预计解除时间

#### 8.4 注意事项

- 禁止随意标记 Pass，需严格按预期结果核对


### 9. 使用建议

#### 9.1 编写流程

1. 确定测试模块和用例编号
2. 编写清晰的用例标题
3. 列出前置条件
4. 描述执行步骤
5. 定义预期结果
6. 执行测试并记录实际结果
7. 标记测试结果

#### 9.2 质量检查清单

在提交测试用例前，检查以下项目：

- [ ] 用例编号是否全局唯一
- [ ] 模块划分是否与产品一致
- [ ] 标题是否简洁明确（≤30 字）
- [ ] 前置条件是否完整具体
- [ ] 步骤是否可独立执行
- [ ] 预期结果是否可验证
- [ ] 实际结果是否如实记录
- [ ] 测试结果是否正确标记

```json
      "已注册账号：13800138000",

      "点击【获取验证码】",

    ],
    "expect_results": [
      "页面跳转至首页",
      "首页显示用户昵称",

    ],
    "actual_results": [

      "本地存储 token 有效"
    ],
    "test_result": "Pass",

```
